# Decisions

Choices made where the spec left room, newest last.

1. **Test framework: Catch2 v3**, fetched with CMake `FetchContent` (or an installed Catch2 3.x if found). Simpler single-dependency setup than GoogleTest.
2. **Minimum CMake 3.24**, for `FetchContent` `FIND_PACKAGE_ARGS` and presets v6.
3. **Core target layout:** one static library `ztrip_core` with public headers under `core/include/ztrip/`. Subsystem folders (`analysis/`, `graph/`, ...) add sources to that one target as they land rather than becoming separate libraries.
4. **CI:** GitHub Actions builds and tests on Ubuntu 24.04 (GCC) and Windows 2022 (MSVC), matching the v1 platforms.
5. **License:** private for now; no license file is added.
6. **Name: `ztrip`**, matching the repository, replacing the spec's working name `mre` in namespaces, targets, CMake options and header paths.
7. **WAV only for file decode in Phase 1**, with an in-house parser (`ztrip::io::read_wav`). It has no dependencies and covers the reference tracks; libsndfile or miniaudio comes in with live capture (Phase 5) and wider formats.
8. **pffft from its maintained fork** (marton78/pffft, tag v1.1.0), compiling only `pffft.c` and `pffft_common.c` into a private static library.
9. **Onset flux is SuperFlux-style** (previous frame max-filtered over +-1 bin) and averaged per bin. Plain per-bin flux let bass-note leakage split kicks into early/late pairs in the Sub band at FFT 2048; the max filter raised Sub-band kick precision on reference track 1 from 0.56 to 0.85 at the same recall.
10. **Beat tracking uses equal-weight band flux**, not full-spectrum flux, and a tempo prior of 120 BPM with a 0.5 octave spread. Full-spectrum flux locked onto off-beat open hats on track 1; a 1 octave prior picked the half-tempo reading (65 BPM) for track 3. Users can move the prior with `--bpm-prior`.
11. **Reference audio stays out of the repo.** Accuracy tests read it from `ZTRIP_REFERENCE_TRACKS` and skip when it is unset, since tracks 02 and 03 are CC BY and would need attribution wherever the repo is distributed. Unit tests use deterministic synthetic drums instead.
12. **Downbeats are a heuristic** (best of `beats_per_bar` phases, fixed for the whole track). Meter changes and pickup bars are not handled; the Phase 4 tempo map with manual nudge covers those.
13. **The graph steps on a fixed 120 Hz tick grid**, matching the analysis signal rate, not the host frame rate. Stateful nodes (Smooth, ADSR, Impulse Decay, Threshold) would otherwise give different results at different frame rates or seek orders. Hosts see values quantised to 1/120 s; interpolation between ticks can come later if 120 Hz looks steppy.
14. **Node state is a slice of one `double` array** owned by the evaluator, and node objects are const while evaluating. That makes checkpoints a plain copy and hot swap a copy by node id.
15. **Unconnected Continuous inputs read a number param of the same name**, so `{"b": 0.5}` sets a constant input and the same param can be promoted to a macro, without separate "default input" machinery.
16. **Implicit port conversions:** Trigger and Clock outputs may feed Continuous inputs (velocity on the firing tick, beat position); Continuous may feed Clock. Continuous never feeds Trigger: that needs a Threshold node, so edge detection is explicit.
17. **Node type names** are PascalCase (`ImpulseDecay`, `BeatLFO`); the spec's "Gate/Threshold" is `Threshold` (its outputs include `gate`). Graph-level problems are diagnostics, unknown params are warnings (so newer files still load), and everything else that is wrong is an error.
18. **Changing a macro, a source binding or the graph** keeps playback going from the current state but invalidates checkpoints, so the next seek (or re-evaluating the paused frame) replays from 0 with the new settings. That keeps "seek equals play" true for the current settings at the cost of one replay per change while paused.
19. **nlohmann/json 3.11.3** from its release tarball (no test data download), linked privately into `ztrip_core`; public headers use a `std::variant` param type instead of exposing the JSON library.
20. **Curve points are a flat number list** (`[x0, y0, x1, y1, ...]`) in `ParamValue`; the loader also accepts `[[x, y], ...]` and flattens it.
21. **Tempo scoring counts the subdivision, and beat tracking skips the Sub band.** Each tempo scores its autocorrelation plus the autocorrelation at twice its rate (the eighth-note pulse). Without that, plain autocorrelation read track 02 at 118 BPM, a 4:3 relation to the 89 BPM that librosa found and that holds up when clapping along. Sub (20-60 Hz) is one or two bins at FFT 2048 and sees kicks late, which made the beat phase wander on track 02. With both changes, tracks 01-03 read 128, 88.5 and 130 BPM. Track 01's beats and downbeats still match the truth exactly, and on tracks 02 and 03 the beats land on onsets about as strong as librosa's beats do.
22. **Versioning:** the version is set once in the top-level `CMakeLists.txt` (`project(VERSION)` plus `ZTRIP_VERSION_PRERELEASE`), starting at `0.1.0-beta.1`; release tags are `v` plus that full version, and the release workflow refuses a tag that disagrees. The pre-release label stays out of `project()` because CMake versions are numeric only.
23. **Beta archives:** one CPack archive per platform (`.tar.gz` for Linux, `.zip` for Windows) holding `analyze-cli`, the static `ztrip_core` library with headers and a `find_package(ztrip)` CMake package, docs, examples and third-party licenses. Linux builds on Ubuntu 22.04 with GCC 12 and links libstdc++ statically into `analyze-cli` so it runs on glibc 2.35+; Windows bundles the MSVC runtime DLLs. A tag creates a draft GitHub release only, so publishing is always a manual step.
24. **A beat is one count of the meter** (a 1/denominator note) and BPM counts those beats, so 6/8 has six beats per bar. Grid divisions (1/1 to 1/64, triplets) are note values converted with the meter's denominator.
25. **Beat 0 is the first downbeat**, at the tempo map's offset plus nudge. A pickup is negative beats, and bars before bar 0 use the bar 0 meter. Nudge is stored apart from the offset so re-fitting the tempo map to new beats keeps the user's alignment.
26. **Tempo conversion uses closed-form integrals** of each curve (step, linear in beats, exponential) and their inverses, with seconds at each segment start cached on edit, instead of the spec's 1 ms lookup table. Lookups are a binary search over segments, exact to rounding in both directions, with no table to keep in sync. The last segment holds `bpm_start`, since a ramp needs an end beat.
27. **The tempo map from analysis passes through the detected beats**: runs of beats that stay within 10 ms of a straight line become one Step segment ending on a detected beat, and beat 0 is always a segment boundary. A steady track gives one segment, and a drifting live band is followed beat by beat. A wrong beat grid stays wrong, and nudge and `scale_tempo` are the manual fixes.
28. **Auto-draft drops ghosts and only snaps nearby hits.** Events under 0.3x the lane's median velocity are dropped. On track 01, all 20 false Sub-band kicks (bass bleed) had velocity 0.17 or less and every true kick 0.2 or more, and dropping them took the drafted kick lane from 85% to 99% precision. Hits move to the 1/16 grid only when the grid point is within 35 ms, so a stretch where the grid is off keeps hits where they were heard. The Kick lane reads the dedicated kick detector's `kick` events when the analysis has them and falls back to `onset.Sub` (the numbers above), so it picks up the detector without a change; `--kick-events` in analyze-cli overrides it.
29. **Envelope times are in beats**, like all authored timing, so an ADSR stretches with the tempo. Note Sequence lanes reach graphs through a `NoteLane` node and `Evaluator::bind_sequence`; a bound tempo map (`bind_tempo`) also drives `BeatClock` in place of the raw beat grid.
30. **Tempo maps save as their own `ztrip.tempo` JSON** (`*.tempo.json`), shaped to embed later as the `tempo_map` object of `project.json`, which doesn't exist yet.
31. **Kicks come from a dedicated detector, not the Sub band.** Sub-band flux at FFT 2048 also fired on off-beat bass notes (F1 at 44 Hz sits in Sub), so kick precision on track 01 was 0.85, and its timing is tied to the FFT hop. The detector measures the jump in low-passed (150 Hz) energy in dB over 10 ms in the time domain: a kick lands on a decayed tail and jumps 15-30 dB, while a bass note entering over the kick's ring jumps a few dB. Track 01 goes to precision 1.00, recall 1.00, mean error 0.7 ms (the Phase 4 bar is 20 ms). Rejected: HPSS before band flux (the kick's 45 Hz tail is as horizontal as a bass note at this resolution, precision fell below 0.2), smaller FFTs (0.91 at best), and a broadband click test (hats and saw bass share the off-beat). On live mixes a plucked bass guitar can jump as sharply as a kick. The default jump is 12 dB, not 9: in a blind A/B listening test the 12 dB clicks were preferred on track 02 (253 kicks instead of 371), and track 01 is exact at either. Track 03, where the kick sits under a busy sustained bass line, sounded off at both settings. `--kick-rise` trades misses for false hits, and a drum stem from offline stem separation (not yet scheduled) is the fuller answer.
32. **Godot host targets Godot 4.5+** through godot-cpp's `godot-4.5-stable` bindings, built with CMake from the main tree (`ZTRIP_BUILD_GODOT`, the `godot` preset) rather than SCons, so the core and the host share one build. With the host on, everything is position independent and MSVC uses the static runtime (`/MT`) that godot-cpp links by default; exceptions stay on because the core reports load errors with them.
33. **One library build, `template_debug`,** serves the editor and both export kinds in `ztrip.gdextension`. A separate `template_release` build can come with the release archives (decision 23).
34. **Graph targets are Godot paths in Phase 3:** a `PropertyOut` target is read directly as `<node path>:<property path>` relative to the player's `target_root`. The spec's per-host `bindings.json` mapping is deferred to the Unreal host (Phase 6), when one graph needs two hosts' paths.
35. **Song time comes from the AudioStreamPlayer**, not frame time, so lights stay locked to what is heard: playback position plus time since the last mix minus output latency, with backwards jitter under 100 ms ignored. In Movie Maker mode the position is used as is, which keeps rendered videos in sync (track 01: light flashes within 13 ms median of the true kicks at 30 fps).
36. **Write-back keeps the pre-graph value per target** from the first write, rather than re-reading it every frame, because the binder is the only writer while a graph runs (layers come later). Restores happen on deactivate, exit tree, graph reload and editor save, so graph-driven values never get saved into a scene.
37. **The graph panel is GDScript**, over the same dictionary shape as the JSON file, with the node catalog, checks and canonical writing done by the core through `ZtripGraphTools`. GraphEdit's port types mirror the core's implicit conversions (Trigger and Clock into Continuous, Continuous into Clock).
38. **The Godot player owns the song's timeline** (`ZtripTimeline`: a tempo map and a Note Sequence) and binds it to the graph's `main` slot. Without `tempo_file`/`sequence_file` on disk it drafts both from the analysis, in memory, and drafts again when the song changes; once loaded from or saved to files it never drafts over them. Drafts fill Kick (kick detector, else Sub onsets), Snare (Mid onsets, min velocity 0.35) and Hats (Air onsets, 0.4), and the demo stage's three onset lights now play those lanes, so editing a note changes what the light does.
39. **The Timeline panel lays time out in seconds**, not beats, so the song's loudness stays fixed and the bar grid and notes move when the tempo map is nudged or scaled, which is what aligning by ear needs. Notes are edited in beats and snapped through the tempo map.
40. **Timeline undo is the panel's own** stack of tempo and sequence JSON snapshots (Ctrl+Z in the panel), because the timeline is not a Godot Resource that `EditorUndoRedoManager` could track. Saving is explicit (**Save** in the panel), separate from saving the scene.
41. **Genre reference tracks come from E-GMD drummers plus synthesized parts.** ztrip is mostly for metal, EDM and rock, and tracks 02 and 03 (folk and jazz) have soft kicks that say little about those. No CC0 or CC BY full mixes in those genres were reachable from the build environment, so tracks 04-08 and 12 take real human drum performances from the Expanded Groove MIDI Dataset (CC BY 4.0, played to a click on an electronic kit and rendered through metal, rock, 909 and drum-and-bass kits, so every hit is known) and add synthesized bass, guitar or synths on the click grid, with their low end 6 dB under the drums. Tracks 09-11 are fully synthesized (CC0) for cases a drummer recording lacks: 16th double kick, blast beats, a sidechained sub and reese bass, picked 8th bass and floor-tom fills. All have ground truth; none is in the repo (decision 11). The generator and E-GMD stems live with the tracks.
42. **Kicks are a jump in low-band amplitude against the loudest low end nearby, not a jump in dB.** The dB-rise detector (decision 31) needed the kick to land on near silence. On the genre tracks it missed kicks over a sustained or sidechained bass (EDM recall 0.06: the kick rises 3-5 dB over a full-level sub), missed double-kick runs (each kick lands on the previous one's ring), and fired on snare bodies and quiet bass plucks that rise from silence. Now a kick is a rise in 150 Hz low-passed RMS amplitude over 20 ms of at least 0.4 times the loudest low-band amplitude within 1.5 s, peaking within 5 dB of the loud low end, with the stronger of two hits within 60 ms kept, then timed at the steepest 5 ms dB rise nearby. Mean kick F over the nine genre tracks went from 0.45 to 0.80 (precision 0.90-0.98 on the six real drummers), with track 01 still exact (P 1.00, R 1.00, 1.4 ms). Rejected: lower cutoffs (snare bodies pass less, but so do kick bodies), a second 70-150 Hz "punch" band (+0.01 F), an attack-sharpness test against sidechain swells (the 10 ms envelope blurs kicks as much as swells), a learned per-track gate, and a gate against the local rather than global loud end (worse on every track here, though it would suit songs with quiet intros). Kicks more than 5 dB under the loud end are dropped; on a mix they are as loud as the bass and indistinguishable from it in the low band. `--kick-jump` and `--kick-gate` replace `--kick-rise`.
43. **Snares get their own detector.** Band onsets can't tell a snare from a kick's beater click, a hi-hat or a guitar chug, and "snare → flash" is a core use. A snare is a jump (as in decision 42) of at least 0.3 in 1-4 kHz with a 4-10 kHz jump of 0.2 at the same moment, peaks within 4-6 dB of the loud end of 1-4 kHz, 4-10 kHz and the 150-350 Hz body, and 1-4 kHz still within 15 dB of its peak 40-60 ms later. That last test is the snare wires ringing, and it took track 01 from F 0.61 to 0.95 by dropping kick clicks. F is 0.86-1.00 on the synthetic genre tracks and 0.70-0.77 on three of the six drummers. On 08 and 12 it is about 0.4 because their truth is full of ghost notes (on hits of velocity 60 or more, recall is 0.84-0.89 at precision 0.97); on 06 the Fat Rock kit's kick clicks still pass as snares (precision 0.39). Claps count as snares.
44. **Drum hits check the tempo and steer the beat phase.** On the genre tracks the onset autocorrelation and the 120 BPM prior read 180-200 BPM metal and rock at half or two-thirds speed, and the off-beat bass and open hats of a disco/house groove pulled the beat grid onto the off-beat. Now the estimate's related tempos (x1/2, x2/3, x3/2, x2) are tracked too and scored by how well their beats fit the kick and snare hits (share of beats on a hit, share of hit velocity on a beat). One replaces the estimate only if its fit is at least 0.5, at least 55% of its beats land on a hit, and it beats the estimate by 0.1, so tracks without clear drums keep the old reading (02 stays at 89 BPM and 03 at 130). Beats are then tracked on the onset strength plus a quarter-weight curve of the drum hits. Tempo is now right on 9 of the 10 truth tracks (was 6) and beat F is 0.97 or more on 8 (was 6). Drum and bass still reads 85 instead of 170: its two-step kick and snare fit both readings about equally. The drum steering moves about a fifth of track 02's beats; a blind A/B of old and new clicks is in the shared folder for a listening check.
45. **The beat tracker is held tight to the tempo** (`tightness` 1600, was 100). At 100 the dynamic-programming tracker slipped half a beat onto louder off-beat hits and back, leaving pairs of short gaps: 20 on track 02 and 2 to 31 on seven of the nine genre tracks. The tempo map follows every detected beat (decision 27), so the Timeline showed track 02, a live band at 88.5 BPM, as 116 BPM at bar 1 with segments from 74 to 119 BPM. At 1600 no track has a gap more than 8% off its median, track 02's tempo map stays between 85 and 94 BPM, track 09's beat F rises from 0.75 to 1.00, and no other track's beat F drops. The trial tracks that check related tempos against the drum hits (decision 44) keep the old 100 (`check_tightness`): held tight, the x3/2 trial on track 04 lands just under the precision bar and the song reads 120 instead of 180.
46. **Live analysis reuses the offline pieces, a frame at a time.** The STFT, band energy, band flux, centroid and envelope follower were split into per-frame helpers (`FrameTransform`, `frame_energy_db`, `BandFlux`, `frame_centroid_hz`, `EnvelopeFollower`) that the offline functions now call, so tuning them changes both modes; offline output is unchanged. What can't be causal is replaced, not forked: whole-file percentiles become a running floor and peak, the centred median a trailing one, and onset peaks are confirmed one hop late. The live FFT is 1024 (hop 256), not 2048, because the window is latency: on track 01, live Sub onsets reach the kicks 12 ms late on average and 15 ms at worst, inside the 30 ms Phase 5 budget with room for a device buffer. The dedicated kick and snare detectors and the beat tracker look ahead (a 1.5 s reference window, a whole-file tempo), so live `kick`, `snare`, `beat` and `downbeat` stay empty until causal versions land; until then, `onset.Sub` with `min_velocity` 0.3 is the live kick.
47. **Live values are stamped when known, on the sample clock.** A live onset is stamped at the frame that confirms it, not at the earlier peak, and `LiveAnalyzer::time()` is the latest analysed frame. A host that evaluates at `time()` then can never have passed an event's tick before the event exists. Time is the count of samples pushed (plus silence for samples a capture ring dropped), so the clock follows the audio device, and output depends only on the samples, not on block sizes, which a test checks bit for bit.
48. **Live analysis runs on the evaluating thread.** Capture threads only copy samples into a lock-free SPSC ring; the thread that evaluates the graph drains it into the analyser before each evaluate. The result is then only ever touched by one thread, so source nodes read it without locks, at the cost of the analysis running in the game frame (a few hundred FFTs of 1024 per second). Live buffers grow with the session (about 25 MB an hour); trimming the past is left for later.
49. **CI fits the free private-repo Actions quota.** GitHub Free gives a private repository 2,000 Actions minutes a month, each job rounded up to a whole minute and Windows minutes counted double. The old CI ran eight jobs per push (three compilers x two configs, plus the Godot host on Linux and Windows): about 80 billed minutes a run, most of it the two Godot builds compiling godot-cpp (17 and 19 minutes), and the quota ran out in one busy day. Now non-draft pull requests build and test Linux GCC release only; pushes to main add the Godot host on Linux; Windows MSVC and the Windows Godot host run weekly (Monday 06:00 UTC), on manual dispatch (Actions > CI > Run workflow) and in the release workflow, which no longer runs on pull requests. Compiles go through ccache and the FetchContent sources are cached, both saved from main; docs-only changes skip CI. The Linux Clang and Debug builds are gone. The cost is that a Windows-only or Clang-only break shows up at the weekly or release run instead of on its pull request, so dispatch the full run before merging anything platform-specific.
